Chrome DevTools extension · OWASP Core Rule Set

CRS Request Inspector

Installation & user guide — see which OWASP CRS / ModSecurity WAF rules your requests would trigger, where they match, and how to read paranoia levels and anomaly scores.
Bundled rule sets: CRS v4.30.0 · v4.25.2 (LTS) · v3.3.10Everything runs locally – no request data leaves your browser

1What the extension does

A Web Application Firewall (WAF) such as ModSecurity, Coraza or Azure Application Gateway / Front Door uses the OWASP Core Rule Set (CRS) to block attacks. CRS is generic – legitimate requests (signed URLs, rich text, JSON with special characters, unusual HTTP methods) can trigger it too. This extension runs the real CRS rules against your requests before they hit a WAF, so you see what would be blocked, which rule fires, on which part of the request, and why.

FeatureWhat it gives you
DevTools tab “OWASP CRS”Next to Network. Every request of the inspected page is analysed automatically while DevTools is open.
Paste a requestChrome “Copy as PowerShell / cURL / fetch”, “Copy all as …”, raw HTTP or HAR files – analysed instantly.
Verdict + paranoia matrixBlocked / passes at your configured paranoia level, and the score at PL1–PL4 (“would start blocking at PL2”).
Rule cardsRule id with link to its source, the request part (JSON field, query arg, cookie, header, path), the matched text highlighted, decoding steps, the regex / libinjection fingerprint.
Exclusion helperCopy-ready ModSecurity/CRS rule exclusions and an Azure WAF exclusion for false positives – test them immediately in the settings.

Accuracy. The engine is a JavaScript re-implementation of ModSecurity v2 running the unmodified CRS rule files. It passes 99.9 % of the official CRS regression tests (5162/5166 for v4.30.0). Your production WAF may still differ in version, paranoia level, limits or exclusions – treat the result as “what a standard CRS installation would do”.

2Install the extension in Chrome

The extension is not in the Chrome Web Store; it is loaded “unpacked” from the project folder. This takes about a minute and only needs to be done once.

  1. Open the extensions pageType chrome://extensions into the address bar and press Enter (or menu ⋮ → Extensions → Manage Extensions).
  2. Turn on Developer modeSwitch on the Developer mode toggle in the top-right corner.
  3. Click “Load unpacked”Three new buttons appear. Click Load unpacked.
  1. Select the extension folderIn the folder picker, open the project and select the folder named extension (the one that contains manifest.json), e.g.
    C:\Users\<you>\src\crs-request-inspector\extension, then click Select Folder. Do not select the project root or extension\src.
  2. Check that it is installedA card CRS Request Inspector appears. Make sure its toggle is on.
  3. Optional: pin the toolbar iconClick the puzzle icon 🧩 in the Chrome toolbar and pin CRS Request Inspector. Clicking the icon opens the analyser in a normal tab for pasting requests without DevTools.

Updating. When the files change (e.g. new rule sets), click ↻ on the extension card, then close and reopen DevTools. Chrome may occasionally show a notice about developer-mode extensions at start-up – choose to keep the extension.

Permissions. The extension only requests storage (for its settings). It reads requests through the DevTools API of the tab you are inspecting and never sends data anywhere.

3Open the OWASP CRS tab in DevTools

  1. Open DevTools on your applicationPress F12 or Ctrl+Shift+I on the page you want to test.
  2. Select the “OWASP CRS” tabIt sits in the DevTools tab bar next to Network. If the window is narrow, it is hidden behind the » overflow button.
  3. Reload the pageRequests are captured from the moment DevTools is open, like the Network tab. Press F5 to capture the full page load, then use the application normally – every request appears in the list as it completes.

Nothing appears? DevTools must be open before the requests are made – reload the page. The red ● record button in the toolbar must be on. Use Preserve log to keep entries across page navigations.

5Paranoia levels (PL1–PL4) and anomaly scores

CRS does not block on a single “bad pattern”. Every matching rule adds points to an anomaly score; the request is blocked when the score reaches the threshold. The paranoia level decides which rules take part.

What a paranoia level is

Every CRS rule belongs to one paranoia level (tag paranoia-level/N). A WAF configured with PLn runs all rules from PL1 up to PLn. Higher levels add stricter rules: more attacks detected, but also many more false positives on normal traffic.

LevelStrictnessTypical use and false-positive risk
PL1Baseline (default)Recommended starting point for almost every application. Few false positives; blocks clear attacks (SQL injection, XSS, path traversal, …). Most managed WAF setups run at this level.
PL2ElevatedApplications with sensitive data. Adds more SQL/XSS/RCE patterns and checks on special characters. False positives are common with free text, rich text, tokens and signed URLs – needs tuning.
PL3HighBanking / high-security. Counts special characters, very strict protocol checks. Many false positives; requires a dedicated tuning effort.
PL4ParanoidExtremely strict (e.g. allows only a very small character set in arguments). Nearly every real application needs extensive exclusions.

How the score works

Rule severityPointsEffect with the default threshold 5
CRITICAL+5One hit is enough to block.
ERROR+4Blocks together with any other hit.
WARNING+3Needs at least one more hit.
NOTICE+2Needs further hits.

A rule that matches in several places (e.g. two query parameters) adds its points for each match. At the end of the request phase, rule 949110 compares the total with the threshold and denies the request with HTTP 403 (shown as 949110 DENY 403 in the verdict). Responses are scored the same way with the outbound threshold (default 4, rule 959100).

Reading the PL matrix

The numbers are cumulative: the PL3 box is the sum of all hits from PL1, PL2 and PL3 – exactly what a WAF configured with PL3 would compute. The toolbar PL buttons choose the blocking level you want to simulate; the extension always also evaluates up to PL4 (detection level, see Settings) so you can see what would happen if you raised it.

Which PL does our WAF use? Ask whoever manages the WAF policy (or check its configuration: tx.blocking_paranoia_level in CRS 4, tx.paranoia_level in CRS 3, the managed rule set and disabled rules in Azure). If unknown, assume PL1 and threshold 5.

6Reading a rule card

Click a rule in the findings list to expand it. Every card starts with a How to fix box (section 7), followed by the technical details. Example: rule 942440 matching a signed image URL.

  • 1Rule header. Rule id (links to the exact line in the CRS source on GitHub), severity, paranoia level, points added (+5), attack category and the rule's message. only at PL2+ = does not count at the selected PL.
  • ✓How to fix – assessment (likely false positive / review / attack / policy), what the rule looks for, and concrete changes for the application, the WAF and Azure WAF – see section 7.
  • 2Where – the part of the request that matched, in plain words (Query arg “Signature”, JSON body field “content”, Cookie “session”, Header “User-Agent”, URL path) and the ModSecurity variable name (ARGS:Signature) you need for exclusions.
  • 3Matched – the value, with the part that triggered the rule highlighted. The value is shown after decoding (see 4); expand Original value to see it as sent.
  • 4Transforms – how the WAF normalised the value before matching (URL-decoding, HTML entity decoding, lower-casing, comment removal …). Attackers use encodings to hide payloads; the WAF decodes first.
  • 5Operator – the test that fired: @rx regular expression (copyable), @detectSQLi/@detectXSS with the libinjection fingerprint, @pm keyword list, etc.
  • 6Inspects – all request parts this rule looks at. Chained – extra conditions that must also be true (here: the value must not look like a JWT).
  • 7Log data – exactly what the WAF would write to its audit log (useful to match against WAF logs).
  • 8Actions – copy rule id / value, show the rule's SecLang source, open the Exclusion helper (section 9), open the rule file on GitHub.

Notes above the findings explain how the request was interpreted – e.g. PARSER “Detected HTTP/2 pseudo-headers …” (Chrome sends HTTP/2; the :authority, :path … headers are not real headers) or a body that could not be parsed as JSON (ModSecurity rejects such requests with rule 200002).

7Recommendations & issues report

For every finding the extension explains what to change – so developers know whether to fix the website or ask for a WAF exclusion.

AssessmentMeaning and typical action
Likely false positiveThe matched value is random data – a JWT, signature, base64 token, hash or UUID. It only looks like attack syntax. Action: WAF exclusion for that variable (or, if your code generates it, a format without special characters).
Review – probably legitimate inputUser-entered text or HTML (reviews, comments, search). Usually legitimate. Action: confirm the server handles it safely (parameterised queries, output encoding, no shell/eval), then exclude only that field on that endpoint.
Looks like an attack payloadA strong PL1 signature (libinjection SQLi/XSS, path traversal). Action: if this was normal application traffic, find out why the app produces such a value – otherwise the WAF is doing its job.
Protocol / policy issueThe request breaks a policy (method, content type, missing header, size limit). Action: fix the client, or adjust the WAF policy (e.g. allowed methods).
Information leakThe response shows error details or stack traces. Action: disable detailed errors in production.

Issues report – all findings in one list

Click Issues report in the toolbar. All findings of the captured requests are grouped by rule + request part with the number of requests, the affected endpoints (ids generalised, e.g. /orders/:id) and the recommendation. Findings that count at your paranoia level come first. Copy as Markdown / Download .md produce a report you can paste into a ticket or pull request.

8Worked examples (demo shop)

These examples come from the fictitious Example Shop in demo/ (node demo/server.mjs, then open DevTools → OWASP CRS and click Browse normally / Send attack samples). They are typical of what the panel finds on real applications.

Signed image URLs

Product images are loaded through a CDN with signed URLs, e.g. /images/products/1042/hero.webp?Expires=…&Signature=…&Key-Pair-Id=….

PLScoreWhy
PL10 · passNo PL1 rule matches – at the default level these requests are fine.
PL25 · blockThe Signature value is URL-safe base64 and contains -- and ~. 942440 “SQL Comment Sequence Detected” sees -- (an SQL comment) → +5 = blocked.
PL3–411–28 · block942431/942432 count special characters, 920273 rejects characters outside a strict set.

Conclusion: at PL1 nothing is blocked. If the WAF runs at PL2 or higher, every product image would get a 403 – a classic false positive. The signature is random data, not user input, so it is safe to exclude ARGS:Signature from the SQL-injection rules for the /images/ path.

Product reviews (free text)

POST /api/products/1042/reviews sends {"rating":5,"text":"Great sound! Select the 'bass boost' mode from the app – it works where others don't."}. At PL1 it passes; at PL2 rules such as 942200 see SQL-like words and quotes (“Select … from”, ') and the score reaches 15. The text is legitimate, but it is user input: keep it parameterised/escaped in the application and, if you run PL2, exclude only ARGS:json.text on the reviews endpoint.

Session cookie containing a JWT

Almost every request shows hits on 942420 (PL3) and 942421 (PL4) – “Restricted SQL character anomaly detection (cookies)”. The cause is the shop_session cookie: it holds a full JWT whose signature contains many - characters, which these rules count as SQL special characters.

  • Impact: none at PL1/PL2 – and Azure WAF does not run PL3/PL4 rules at all.
  • Application option: store an opaque random session id in the cookie and keep the JWT server-side – smaller cookies, no special characters, token not exposed to the browser.
  • WAF option (only if you run CRS at PL3+): exclude REQUEST_COOKIES:shop_session from 942420/942421.

PUT / PATCH / DELETE API calls

PUT /api/account/profile scores 5 at PL1 because of 911100 “Method is not allowed by policy”: standard CRS allows only GET, HEAD, POST and OPTIONS. This is a WAF policy question, not a bug in the request – see section 10 for why it may not be blocked in your environment.

Client-side encoded fields

Some applications encode free text on the client (base64, hex) before sending it. Encoded content passes the WAF because the WAF cannot read it – the same effect as an exclusion, but invisible to whoever operates the WAF. That is acceptable only if the server validates and safely handles the decoded text; an explicit, documented exclusion for that one field on that one endpoint is the more transparent alternative.

Real attack or false positive? Ask: does the matched value come from a user, and could it reach a database, a shell or an HTML page? Random tokens, signatures, hashes and encrypted blobs → false positive. Free text from a form, search box or review → real risk; exclude only narrowly (one field, one endpoint) and make sure the application escapes/parameterises it.

9Fixing false positives with exclusions

Click Exclusion on a rule card. The helper generates snippets for the matched variable and endpoint – ids, numbers and UUIDs in the path are generalised ([^/]+, [0-9]+).

SnippetWhen to use
Runtime exclusion — this endpoint, this variablePreferred. Removes one variable from one rule on matching URLs only. Goes into the rules loaded before CRS.
Runtime exclusion — this endpoint, whole ruleWhen the rule hits many variables on that endpoint.
Configure-time — everywhere, this variableThe variable is never dangerous anywhere (e.g. a CSRF token). Goes after CRS.
Azure WAFExclusion JSON for Application Gateway / Front Door WAF policies (match variable, selector, rule).

Verify an exclusion before rolling it out

  1. Copy the snippetUse the Copy button next to it.
  2. Paste it into the settingsOpen settings (⚙), paste it into Custom rules before CRS (runtime exclusions) or after CRS (SecRuleUpdateTargetById), click Apply.
  3. Check the resultAll requests are re-analysed. The rule should disappear from the card list and the verdict should change to Passes. Then hand the snippet to the WAF owner.

10Why the extension and Azure WAF can disagree

With the default profile the extension shows what a standard CRS installation in blocking mode would do – load your own policy (section 11) to simulate your actual Azure WAF. If a request it marks as blocked goes through in your environment, the WAF in front of the application is configured differently – or is not enforcing at all.

Which WAF is in front of the site?

Look at the response headers in the Network tab: x-azure-ref means the site is served through Azure Front Door; Application Gateway WAF usually leaves no header but answers blocked requests with its own 403 page. Azure WAF policies use Microsoft's Default Rule Set (DRS 2.x – based on CRS 3.3 plus Microsoft rules), not the open-source CRS 4 that the extension uses by default – switch the profile to Azure WAF and import your policy (section 11) for an exact simulation.

Possible reasonExplanation
Policy in Detection modeAzure enables managed rules in Detection mode by default: matches are only logged, nothing is blocked. Very common in dev/test environments.
Front Door Standard tierManaged rule sets (DRS) are only available on Front Door Premium (and classic). On Standard only custom rules exist – no CRS-style detection at all.
No WAF policy on this domainThe WAF policy must be attached to the endpoint / domain through a Front Door security policy.
Rule disabled or excluded911100 (or another rule) may be disabled, set to Log, covered by an exclusion or by a custom Allow rule.
Different rule setDRS differs from CRS 4: no PL3/PL4 rules, PL2 rules disabled by default in DRS 2.2, some rules replaced by Microsoft rules (e.g. 942440 → 99031002). The How to fix box shows these Azure notes per rule.

How to verify

  1. Check the WAF policyAzure portal → Front Door profile → Security policies → WAF policy → Policy settings: Mode (Detection / Prevention); Managed rules: rule set version and the state of rule 911100. With the Azure CLI: 
    az afd profile show -g <resource-group> --profile-name <profile> --query sku.name
az afd security-policy list -g <resource-group> --profile-name <profile> -o table
az network front-door waf-policy show -g <resource-group> -n <policy> --query "{mode:policySettings.mode, state:policySettings.enabledState, rules:managedRules.managedRuleSets[].{type:ruleSetType, version:ruleSetVersion}}"
  2. Look at the WAF logIf diagnostic logs are sent to Log Analytics, this shows what the WAF decided for the PUT request (action_s = Log / Block / AnomalyScoring): 
    AzureDiagnostics
| where Category == "FrontDoorWebApplicationFirewallLog"
| where requestUri_s has "/api/account/profile"
| project TimeGenerated, ruleName_s, action_s, policyMode_s, details_msg_s, requestUri_s
| order by TimeGenerated desc
  3. Optional live testAn obvious, harmless test string shows immediately whether the WAF blocks: a 403 from Front Door means Prevention mode with managed rules is active; a normal response (e.g. 401 from the App Service login) means the WAF does not block. Inform your security team first – this deliberately triggers a WAF alert. 
    curl -s -o /dev/null -w "%{http_code}\n" "https://shop.example.com/?crs-test=%3Cscript%3Ealert(1)%3C%2Fscript%3E"

12Pasting requests

Useful for requests from colleagues, tickets or other browsers, or to test a modified request.

  1. Copy the request in DevToolsNetwork tab → right-click the request → Copy → Copy as PowerShell (best: includes cookies and user agent), Copy as cURL (bash) / (cmd), Copy as fetch, or Copy all as … for many requests.
  2. Paste into the panelPress Ctrl+V in the OWASP CRS tab or click Paste request. The format is detected automatically; click Analyze (Ctrl+Enter).
FormatNotes
PowerShellRecommended. HTTP/2 pseudo-headers (authority, method, path, scheme) are recognised; cookies from $session.Cookies are included.
cURL (bash / cmd)Includes cookies (-b). Note: cURL copies omit the browser's Accept-Encoding.
fetch / fetch (Node.js)Browser fetch copies contain no cookies and no User-Agent – may cause extra PL2 hits (920320 “missing User-Agent”).

Sensitive data. Copied requests contain session cookies and tokens. The extension keeps them in memory only and never sends them anywhere – but take care where else you paste them.

14FAQ & troubleshooting

QuestionAnswer
The OWASP CRS tab is missing.Check the extension is enabled on chrome://extensions, then close and reopen DevTools. Look behind the » overflow in the tab bar.
The list stays empty.Reload the page with DevTools open; check the record button is red. Requests made before DevTools was opened are not captured.
Images and scripts are listed too.Yes – the WAF inspects every request (cookies and query strings of images can trigger rules). Use the type filters (Fetch/XHR, Doc …) to focus.
Our WAF did not block a request the extension marks as blocked (or vice versa).See section 10: Detection mode, Front Door tier, policy association, disabled rules and DRS differences. Rule ids and the Log data line help to match WAF logs.
DELETE / PUT / PATCH are blocked (911100).CRS only allows GET, HEAD, POST, OPTIONS by default. Most API deployments extend tx.allowed_methods – add the setting shown in section 13. On Azure, see sections 10–11.
Large uploads / bodies are blocked (ENGINE 413).ModSecurity rejects bodies above 128 KB (without files) by default. Your WAF may use a different limit.
“Rule 955100: data file not available”.Windows Defender removed a CRS signature file for web-shell detection in responses. Only that response rule is affected; request analysis is complete.
Is any data sent to a server?No. Rules and analysis run entirely inside the extension.

Glossary

CRSOWASP Core Rule Set – the generic attack-detection rules used by ModSecurity, Coraza and many cloud WAFs.
Anomaly scorePoints accumulated by matching rules; compared with the threshold at the end of the request.
Paranoia level (PL)How strict CRS is (1–4). Higher = more rules, more false positives.
False positiveA legitimate request that triggers a rule.
ExclusionWAF configuration that stops a rule from inspecting a specific variable or endpoint.
ARGS / REQUEST_COOKIES / REQUEST_HEADERSModSecurity names for query/body parameters (JSON fields as json.field), cookies and headers.
